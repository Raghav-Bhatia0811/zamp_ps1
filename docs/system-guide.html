Ledgerline · Invoice Desk

How the invoice system works

This document tells you how Ledgerline changes a vendor invoice PDF into a payment decision. It shows each part, each stage and each check. It also gives the measured accuracy of the results.

Case study: AI Solutions Analyst, PS-1 (Finance / AP) Version: 1.0, 4 Nov 2026 Writing rules: ASD-STE100 Simplified Technical English Scope: the main functions (approximately 80% of the system)
Input
One invoice PDF (digital or scanned)
Output
Approved, On hold or Rejected, with reasons
Checks
13 fixed rules, each with an ID
Measured accuracy
7 of 7 correct decisions in each test set

01Purpose

Ledgerline processes vendor invoices for an accounts payable (AP) team. The input is one invoice as a PDF file. The output is one decision: Approved On hold or Rejected.

The system shows each step while it operates. It also writes the reason for each decision. A person can examine each decision later.

Main design rule

The AI only reads the invoice. Fixed rules make the decision.

Thus, the system always gives the same decision for the same data. The AI cannot approve a payment. Each decision has a list of checks that a person can read.

03The 7 stages

The pipeline does the stages in this sequence. Each stage gets a status: done, warning, hold or fail. The UI shows the status of each stage while it operates.

StageWhat the system doesTool
1. Receive documentCounts the pages. Finds if the PDF has text or is a scan. Makes a fingerprint (SHA-256) of the file.pypdf
2. Read invoiceReads the vendor, GSTIN, invoice number, dates, PO number, lines, tax, total, bank details and notes.AI model, or OCR
3. Identify vendorCompares the GSTIN with the vendor list. If there is no match, compares the name.Rules
4. Validate invoiceChecks the fields, the vendor status, the arithmetic, the GST rate, the bank details and the date.Rules
5. Match purchase orderUses the PO number on the invoice. If there is no PO number, it finds the most probable PO.Rules
6. Run controlsLooks for duplicates. Compares unit prices with the PO. Compares the total with the remaining PO balance.Rules and ledger
7. Decide and routeMakes the decision. Sends the invoice to a queue. Writes the next steps and a draft email.Rules

04The reader

The reader is the only part that uses AI. It changes the PDF into structured fields. All readers give the fields in the same format. Thus, you can replace one reader with a different reader. The rules do not change.

  • The AI model reads only. It does not calculate or correct values.
  • If a value is not on the invoice, the field is empty (null). The AI must not guess.
  • If the AI fails, the system does not stop. It uses the local reader and writes the reason in the log.
  • The reader also gives a list of fields that it read with low confidence. Check R08 shows this list.

05Purchase order match

Each invoice must agree with a purchase order (PO). Some invoices show the PO number. Some invoices do not.

NOTE

The maximum score is 90% because a PO that is not printed on the invoice is never certain. An inferred PO always goes to a person. The system never approves it automatically.

07Duplicate check

A vendor can send the same invoice two times. Sometimes the number has a different format. The system removes symbols and zeros before it compares numbers. Thus, “AFS/0042” and “AFS-42” are the same invoice.

NOTE

The time window is short (7 days) on purpose. Many vendors send the same amount each month for a contract. A long window holds these correct invoices.

08PO balance check

A vendor can split one PO into many invoices. Each invoice can look correct by itself. The system adds all approved invoices for the PO. Then it adds the new invoice. If the sum is more than the PO, the invoice goes on hold.

Example: PO-1002, 20 trips, ₹4,00,000
Invoice 1
₹1,60,000 · paid
Invoice 2
₹1,60,000 · approved
Invoice 3
₹1,20,000 · on hold
Invoiced before This invoice, inside the PO Over the PO by ₹40,000 PO limit

Invoice 3 bills 6 trips. The earlier invoices billed 16 trips. The total is 22 trips, but the PO is for 20 trips. Thus, check R13 fails and the invoice goes on hold.

CAUTION

This check uses the ledger. The result changes with the sequence of the invoices. Process invoice 2 before invoice 3.

09Decision and routing

After all checks, the system makes one decision. A reject check is more important than a hold check.

The system also sends each decision to a queue. The queue tells the team who must do the next step.

CauseQueue
All checks passPayment run
Bank details changedTreasury verification
Unit price or PO balance problem, unknown vendorProcurement
Duplicate, inferred PO, GSTIN or GST rate problemAP review
Fields missing, arithmetic not correctVendor follow-up

When the vendor must send something, the system writes a draft email. The system does not send the email. A person reads it first.

10Live view

The UI shows each stage while the pipeline operates. The diagram shows the messages between the parts.

  • The pipeline saves the run record after each stage.
  • The browser changes only the stage that changed. Thus, the line moves down the timeline.
  • Each stage stays visible for a minimum of 0.45 seconds. You can set this time to 0 with DEMO_PACING_MS=0.

13Accuracy of results

We measured the accuracy with the script scripts/evaluate.py. The script compares each result with the known correct value. The correct values come from the data that made the sample PDFs.

Method

  • Reader: the local reader (pdftotext and Tesseract OCR). We did not measure Claude or Gemini. No AI key was available during the test.
  • Field accuracy: 11 fields for each invoice: GSTIN, invoice number, invoice date, due date, PO number, subtotal, tax, total, bank account, IFSC and all line items.
  • Decision accuracy: the decision is the expected decision.
  • Right reason: the decision is correct, and the expected check caused it.

Light scansAll 7 invoices as scans: 170 dpi, 0.45° skew, light noise.
Heavy scansAll 7 invoices as poor scans: 120 dpi, 0.9° skew, more noise and blur.

What the results show

  1. On digital PDFs, the local reader read all fields correctly.
  2. On scans, the reader made errors in long codes: GSTIN, bank numbers, invoice numbers and line items. Dates and totals were always correct.
  3. No reading error caused a wrong approval. When the reader made an error, a check found a problem. Usually, check R04 (arithmetic) failed. Thus, the invoice went on hold for a person. The system fails safe.
  4. In 2 cases, the decision was correct but the reason was different. Invoice 6 went on hold because of R04 (arithmetic), not R12 (unit price). The person sees a different reason.
  5. If the reader cannot read the bank account, check R06 does not fail. The payment run must always use the account in the vendor master, not the account on the invoice.
WARNING

These results come from 7 invoices in 3 layouts that we made. Real invoices have more formats, handwriting, stamps and pages. Do not use these numbers as the accuracy on real invoices.

Measure the AI reader

We expect an AI reader to read scans better than OCR, but we did not measure it. Do this procedure before the demo:

  1. Set the AI key: export ANTHROPIC_API_KEY=...
  2. Run the script: .venv/bin/python scripts/evaluate.py --engine claude
  3. Read the results in the terminal and in data/eval_claude.json.
  4. Put the new numbers in this section.
CAUTION

The script clears the demo database. Run it before the demo, not during the demo.

14AI model: Claude or Gemini

Claude is not necessary. The case study permits any AI model. In this system, the AI does only one task: stage 2, read the invoice. All other stages are fixed rules. They do not change when the AI model changes.

Gemini can do the same task. It reads PDFs directly, also scanned PDFs. It can also give JSON in a fixed schema. A limit of 1,500 requests is sufficient. One invoice uses one request.

Changes necessary for Gemini

  1. Add a Gemini reader in app/extract.py. It must give the same fields as the Claude reader.
  2. Add the setting GEMINI_API_KEY. When this key is set, the system uses Gemini.
  3. Add a “Gemini” option to the reader selection in the UI.
  4. Keep the local reader as the fallback.
CAUTION

Free keys also have a limit for each minute. Run “Run all seven in order” one time before the demo to make sure that the limit is sufficient.

NOTE

On the free tier, Google can use the data that you send to improve its products. This is satisfactory for the test invoices. For real invoices, use a paid tier or an enterprise agreement.

15Procedure: operate the system

  1. Open a terminal in the folder invoice-desk.
  2. Set the AI key, if you have one: export ANTHROPIC_API_KEY=...
  3. Start the server: .venv/bin/uvicorn app.main:app --port 8000
  4. Open http://localhost:8000 in a browser.
  5. Click Reset demo to clear old data.
  6. Click a scenario, or drop an invoice PDF on the upload area.
  7. Look at the stages while they operate.
  8. Click a stage to see its details.
  9. For an invoice on hold, write a note. Then click Approve and post or Reject.
  10. Click Runs to see the history of all invoices.
CAUTION

If you send the same file two times, the system rejects the second file as a duplicate. Click Reset demo before each new demonstration.

16Assumptions and limits

  • The buyer is one company in India. All amounts are in INR. The system accepts CGST + SGST and IGST.
  • The PO balance uses the subtotal before tax. A different check (R05) examines the tax.
  • The ledger starts with 2 invoices “imported from ERP”. Thus, the duplicate and PO balance checks have history.
  • The upload area replaces an email inbox. The same pipeline can receive invoices from an inbox.
  • The system compares the invoice with the PO only. It does not compare with the goods receipt (no 3-way match).
  • The system does not make payments. It sends approved invoices to the payment run queue.

POPurchase order. The document that approves a purchase before the invoice.
