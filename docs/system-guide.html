Ledgerline · Invoice Desk

How the invoice system works

This document tells you how Ledgerline changes a vendor invoice into a payment decision. The invoice can be a PDF, a scan or a phone photo. The document shows each part, each stage and each check. It also gives the measured accuracy of the results.

Case study: AI Solutions Analyst, PS-1 (Finance / AP) Version: 2.0, 5 Nov 2026 Writing rules: ASD-STE100 Simplified Technical English Scope: the main functions (approximately 80% of the system)
Input
One invoice PDF or image (digital, scan or phone photo)
Output
Approved, On hold or Rejected, with reasons and policy clauses
Checks
16 fixed rules, each with an ID and a policy clause
Measured accuracy
10 of 10 correct decisions in each test set

01Purpose

Ledgerline processes vendor invoices for an accounts payable (AP) team. The input is one invoice as a PDF file or as an image. The image can be a phone photo. The output is one decision: Approved On hold or Rejected.

The system shows each step while it operates. It also writes the reason for each decision and the policy clause for each exception. A person can examine each decision later.

Main design rule

The AI only reads the invoice. Fixed rules make the decision.

Thus, the system always gives the same decision for the same data. The AI cannot approve a payment. Each decision has a list of checks that a person can read.

A second rule applies: the system does not pay on a value that it cannot read clearly. Image clean-up makes a bad page easier to read. Field verification proves each value that it can. If a value is not clear, a person must examine it.

03The 10 stages

The pipeline does the stages in this sequence. Each stage gets a status: done, warning, hold, fail or skipped. The UI shows the status of each stage while it operates.

StageWhat the system doesTool
1. Receive documentAccepts a PDF or an image (JPG, PNG, TIFF or WebP). Uses the EXIF rotation of a photo. Finds if the file is a digital PDF, a scan or a photo. Counts the pages. Makes a fingerprint (SHA-256) of the file.pypdf, Pillow
2. Clean up imageMakes a scan or a photo easier to read. Then measures the legibility of the clean page (check R00). A digital PDF needs no clean-up.OpenCV, Tesseract OSD
3. Find regionsFinds the vendor block, invoice details, bill-to, line table, totals, bank block, stamps, signatures and handwriting. Reads the important regions again at a larger scale. Reads the text of each stamp.YOLO11n, ONNX Runtime
4. Read invoiceReads the vendor, GSTIN, invoice number, dates, PO number, lines, tax, total, bank details and notes.AI model, or OCR
5. Verify fieldsProves each field with check digits, formats, arithmetic and master data. Repairs known OCR errors only when the repair is proven (check R08).Rules
6. Identify vendorCompares the GSTIN with the vendor list. If there is no match, compares the name.Rules
7. Validate invoiceChecks the fields, the vendor status, the arithmetic, the GST rate, the bank details, the date and the signature.Rules
8. Match purchase orderUses the PO number on the invoice. If there is no PO number, it finds the most probable PO. Matches the lines by text or by meaning.Rules and embeddings
9. Run controlsLooks for duplicates. Compares unit prices with the PO. Compares the total with the remaining PO balance. Looks for payment stamps and handwritten changes.Rules, ledger and layout
10. Decide and routeMakes the decision. Sends the invoice to a queue. Adds the policy clause for each exception and similar past decisions. Writes the next steps and a draft email.Rules and search
WARNING

If the page is not legible after clean-up, check R00 fails. Stages 7, 8 and 9 do not operate. The system does not check, and does not pay, values that it cannot read. The invoice goes on hold. The vendor gets a request for a clearer copy.

04Image clean-up

Scans and phone photos are often bad. The page can be at an angle, upside down, dark, noisy or small. Stage 2 makes the page easier to read before the reader starts. A digital PDF has a text layer, so it does not need this stage.

StepWhat the system doesWhen
1. Find the pageFinds the sheet of paper in the photo. Cuts it from the background. Removes the perspective with a 4-point warp.Photos only
2. Turn uprightTesseract OSD finds a page that is sideways or upside down. The system turns it.OSD confidence 1.5 or more
3. Invert dark bandsSome letterheads have white text on a dark band. The system changes this area to dark text on a light background.Large dark bands only
4. Remove shadowsDivides the page by an estimate of the paper background. This removes shadows and uneven light.Photos, and scans with low contrast
5. Remove noiseRemoves speckle and sensor noise.Noise level more than 2.2
6. StraightenMeasures the angle of the text lines. Turns the page to make them horizontal.Angle 0.25° or more
7. Make largerOCR needs approximately 300 dpi. The system makes a small page larger, to a maximum of 3 times.Below 250 dpi
8. SharpenSharpens soft text, if the noise is low. Then increases the contrast.Sharpen: soft text only. Contrast: always

The system does a step only when the page needs it. It writes each step in the log. The UI shows the page as received and the clean page.

NOTE

To find the page in a photo, the system examines the background (the desk) at the edge of the image. It does not look for white paper. A search for white paper cut off a dark letterhead in tests. The vendor name and GSTIN were on that letterhead.

The legibility gate

The system does not guess if a page is legible. It reads the clean page with OCR and measures the result. The score uses the mean OCR word confidence and the quantity of words found:

score = OCR confidence × (0.55 + 0.45 × coverage), where coverage is the number of words divided by 60, to a maximum of 1.

ScoreGradeResult of R00
80 to 100GoodPass
66 to 79FairPass
50 to 65PoorWarning only each value is cross-checked
0 to 49UnreadableHold ask the vendor for a clearer copy

A digital PDF gets a score of 100. The system reads its text directly from the file.

CAUTION

Do not type values from a page that failed R00. AP policy §2.2 does not permit values that are guessed. Ask the vendor for a clear copy, if possible the original PDF.

05Layout detection

Stage 3 finds the regions of the page. A small object detector (YOLO11n) does this work. ONNX Runtime runs the model on the CPU. The system does not need a GPU or PyTorch to run it.

  • On scans and photos, the system reads the vendor block, invoice details, line table, totals and bank block again, each by itself. A small region at a larger scale often gives a better OCR result.
  • A stamp is often in colour and at an angle. The system isolates the ink colour, uses the stamp frame to make it straight, and then reads it.
  • A stamp with “PAID”, “CANCELLED” or “VOID” puts the invoice on hold (R14). Other stamps, for example “RECEIVED”, give a warning only.
  • Handwriting on or near the totals, the bank details or the line items puts the invoice on hold (R14). Handwriting in other areas gives a warning only.
  • A signature on a paper invoice satisfies R15.
  • If the model file is not installed, the stage gives a warning. The reader reads the full page. Checks R14 and R15 do not operate.

06The reader

The reader is the only part that uses AI to read the invoice. It changes the document into structured fields. All readers give the fields in the same format. Thus, you can replace one reader with a different reader. The rules do not change.

  • The AI model reads only. It does not calculate or correct values.
  • For a digital PDF, the AI model gets the PDF. For a scan or a photo, it gets the clean page images from stage 2.
  • The local reader uses the region reads from stage 3 first, for the fields that they contain.
  • If a value is not on the invoice, the field is empty (null). The AI must not guess.
  • If the AI fails, the system does not stop. It uses the local reader and writes the reason in the log.
  • If the AI model reads a scan or a photo, the system also keeps the OCR read. Stage 5 compares the two reads (dual read).

07Field verification

An invoice contains its own proofs. Stage 5 uses them to examine each value from the reader. Each field gets one status.

StatusMeaning
verifiedA check digit, the arithmetic or the master data proves the value.
agreedTwo independent reads (AI model and OCR) gave the same value.
readOne clear read. There is no proof to compare it with.
repairedThe system corrected an OCR error. The UI shows the old value and the new value.
disputedTwo reads do not agree, and no proof shows which is correct.
lowThe value was read with low OCR confidence.
missingThe value is not on the document.

The proofs

  • GSTIN: the last character is a mod-36 check digit. The 15 characters also have a fixed pattern of letters and digits.
  • IFSC: 4 letters, then “0”, then 6 characters. The first 4 letters (the bank code) must agree with the bank name.
  • Account number: 9 to 18 digits only. It is verified if it is the same as the account in the vendor master.
  • Arithmetic: quantity × rate = amount for each line. The lines add up to the subtotal. Subtotal + tax = total.
  • Dates: each date is valid, and the due date is after the invoice date.
  • Master data: a GSTIN in the vendor master proves the vendor name. A PO number in the PO register is verified.

Rules for repairs

  • The system repairs only known OCR errors, for example O and 0, I and 1, 6 and 8.
  • The system repairs a value only when the new value is proven: the check digit passes, the master data agrees or the arithmetic is correct.
  • The system does not repair a wrong amount that the vendor printed. Check R04 fails and the invoice goes back to the vendor.
  • A repaired total or bank account still goes to a person. Check R08 holds the invoice.
  • A repaired GSTIN that is in the vendor master does not need a person. The check digit and the master data prove it (AP policy §4.5).

When a person must examine a value

Check R08 holds the invoice for AP review if one of these conditions is true:

  • The total, invoice number, bank account, IFSC or GSTIN has the status low or disputed.
  • The system repaired the total or the bank account.
  • On a scan or a photo, the totals agree with each other but not with the lines. Thus, the reader probably missed a line. This is a read problem, not a vendor error. The invoice goes to a person, not to the vendor. Check R04 does not fail for this reason.

Stage 5 also gives a confidence score. This score is the mean confidence of all fields that are present.

08Purchase order match

Each invoice must agree with a purchase order (PO). Some invoices show the PO number. Some invoices do not.

NOTE

The maximum score is 90% because a PO that is not printed on the invoice is never certain. An inferred PO always goes to a person. The system never approves it automatically.

Line match by meaning

A vendor can use different words from the PO for the same item. For example, “Photocopy sheets” on the invoice and “A4 copier paper” on the PO. The system first compares the text. If the text is different, it compares the meaning with embeddings (bge-small). A similarity of 0.82 or more is a match.

CAUTION

Model numbers and sizes must agree. “HP 12A” and “HP 88A” are different items, also when the other words are the same. If the model numbers do not agree, the system does not match the lines.

10Duplicate check

A vendor can send the same invoice two times. Sometimes the number has a different format. The system removes symbols and zeros before it compares numbers. Thus, “AFS/0042” and “AFS-42” are the same invoice.

NOTE

The time window is short (7 days) on purpose. Many vendors send the same amount each month for a contract. A long window holds these correct invoices.

11PO balance check

A vendor can split one PO into many invoices. Each invoice can look correct by itself. The system adds all approved invoices for the PO. Then it adds the new invoice. If the sum is more than the PO, the invoice goes on hold.

Example: PO-1002, 20 trips, ₹4,00,000
Invoice 1
₹1,60,000 · paid
Invoice 2
₹1,60,000 · approved
Invoice 3
₹1,20,000 · on hold
Invoiced before This invoice, inside the PO Over the PO by ₹40,000 PO limit

Invoice 3 bills 6 trips. The earlier invoices billed 16 trips. The total is 22 trips, but the PO is for 20 trips. Thus, check R13 fails and the invoice goes on hold.

CAUTION

This check uses the ledger. The result changes with the sequence of the invoices. Process invoice 2 before invoice 3.

12Decision and routing

After all checks, the system makes one decision. A reject check is more important than a hold check.

The system also sends each decision to a queue. The queue tells the team who must do the next step. If many checks fail, the queue of the first failed check applies.

CauseQueue
All checks passPayment run
Bank details changedTreasury verification
Unit price or PO balance problem, line not on the PO, PO not found, unknown vendorProcurement
Duplicate, inferred PO, GSTIN or GST rate problem, critical field not read reliably (R08), payment stamp or handwritten change (R14)AP review
Page not legible (R00), fields missing, arithmetic not correctVendor follow-up

For each check that did not pass, the system shows the text of its policy clause. For an invoice that is not approved, the system also shows up to 3 similar past decisions. Refer to Policy and precedent search.

When the vendor must send something, the system writes a draft email. The system does not send the email. A person reads it first.

13Policy and precedent search

The folder knowledge/ contains the AP policy, the GST notes and 16 past reviewer decisions. The system adds each new reviewer note to this set as a new precedent. The system uses this knowledge for three tasks:

TaskHow it operates
Policy clause for a checkA fixed table connects each check to its clause. This is a lookup, not a search.
Similar past decisionsFor each failed check (up to 3), the system searches the precedents for that same check. It shows up to 3 results. Results for the same vendor come first.
Ask about this invoiceThe reviewer types a question. The system finds 6 policy passages and 3 past decisions. It sends them, with the run record, to Claude. Claude writes a short answer with citations.
  • The search is hybrid. BM25 finds exact words, for example “R06” or “IFSC”. The embeddings (BAAI/bge-small-en-v1.5, ONNX on the CPU) find the meaning, for example “supplier moved banks”. Reciprocal rank fusion (RRF) combines the two lists.
  • If the embedding model is not available, the search uses BM25 only. The system tells you this.
  • Each claim in the answer has a citation, for example [§6.2] for a policy clause, [P-102] for a past decision, or [run] for the run record.
  • The answer gives advice only. It does not approve an invoice. It does not change a decision.
  • If Claude is not connected, or the call fails, the system shows the passages that it found.
NOTE

The search for past decisions is advisory. If the search fails, the decision does not change. The system writes the error in the log.

17Accuracy of results

We measured the accuracy with the script scripts/evaluate.py --engine local --ablation. The script sends each invoice through the full pipeline. It compares each result with the known correct value. The correct values come from the data that made the sample documents.

Method

  • Reader: the local reader (pdftotext and Tesseract OCR). We did not measure Claude or Gemini.
  • Field accuracy: 11 fields for each invoice: GSTIN, invoice number, invoice date, due date, PO number, subtotal, tax, total, bank account, IFSC and all line items. In the original set, the result does not include the fax (sample 9). This page is illegible on purpose, so it has no fields to score.
  • Decision accuracy: the decision is the expected decision.
  • Right reason: the decision is correct, and the expected check caused it.
  • Ablation: the heavy scans and the photos again, with image clean-up and region reads off (VISION_ENHANCE=0, REGION_OCR=0).
Test setContents
OriginalThe 10 samples as supplied: 7 digital PDFs, 2 scans and 1 phone photo.
Light scansAll 10 invoices made again as scans: 170 dpi, 0.45° skew, light noise.
Heavy scansAll 10 invoices as poor scans: 120 dpi, 1.2° skew, more noise and blur.
Phone photosAll 10 invoices as phone photos: angled, with a shadow, on a desk, JPG.

What the results show

  1. With vision on, the system made the correct decision, for the correct reason, for all 40 invoices in the 4 test sets.
  2. The ablation shows the value of the vision stages. Without clean-up and region reads, field accuracy on heavy scans falls from 99.1% to 85.5%. On phone photos it falls from 97.3% to 41.8%. Only 5 of 10 photo decisions are then correct. Image clean-up and region reads make photos usable.
  3. In the original set, only one field is not correct: the total of sample 10. This total has a handwritten strike-through. Thus, the system correctly does not read it, and check R14 holds the invoice. This is the correct result.
  4. If the reader cannot read the bank account, check R06 does not fail. The payment run must always use the account in the vendor master, not the account on the invoice.
WARNING

These results come from 10 invoices that we made, in a small number of layouts. Real invoices have more formats, handwriting, stamps and pages. Do not use these numbers as the accuracy on real invoices.

18AI model: Claude or Gemini

Claude is not necessary. The case study permits any AI model. In the pipeline, the AI model (Claude or Gemini) does only one task: stage 4, read the invoice. The other stages use image processing, two small local models (layout and embeddings) and fixed rules. They do not change when the AI model changes.

The AI also writes the answer for “Ask about this invoice”. This answer gives advice only. Without an AI model, the system shows the passages that it found.

Gemini can do the same reading task. It reads PDFs and images directly, also scans and photos. It can also give JSON in a fixed schema. A limit of 1,500 requests is sufficient. One invoice uses one request.

Changes necessary for Gemini

  1. Add a Gemini reader in app/extract.py. It must give the same fields as the Claude reader. For scans and photos, send the clean page images.
  2. Add the setting GEMINI_API_KEY. When this key is set, the system uses Gemini.
  3. Add a “Gemini” option to the reader selection in the UI.
  4. In app/pipeline.py and app/verify.py, use a Gemini read the same as a Claude read. Thus, the dual read with OCR also operates for Gemini.
  5. Keep the local reader as the fallback.
CAUTION

Free keys also have a limit for each minute. Run “Run all 10 in order” one time before the demo to make sure that the limit is sufficient.

NOTE

On the free tier, Google can use the data that you send to improve its products. This is satisfactory for the test invoices. For real invoices, use a paid tier or an enterprise agreement.

19Procedure: operate the system

  1. Open a terminal in the folder invoice-desk.
  2. Set the AI key, if you have one: export ANTHROPIC_API_KEY=...
  3. Start the server: .venv/bin/uvicorn app.main:app --port 8000
  4. Open http://localhost:8000 in a browser.
  5. Click Reset demo to clear old data.
  6. Click a scenario, or drop an invoice PDF or image (for example a phone photo) on the upload area.
  7. Look at the stages while they operate.
  8. Click a stage to see its details.
  9. Open the document. Compare the tabs As received, Cleaned and Regions.
  10. For an invoice on hold, read the policy clause and the similar past decisions. Type a question in Ask about this invoice, if necessary.
  11. Write a note. Then click Approve and post or Reject.
  12. Click Knowledge to see your note as a new precedent.
  13. Click Runs to see the history of all invoices.
CAUTION

If you send the same file two times, the system rejects the second file as a duplicate. Click Reset demo before each new demonstration.

NOTE

At the first start, the system downloads the embedding model (approximately 65 MB) into models/embed/. Without a network connection, the system uses keyword search only.

20Assumptions and limits

  • The buyer is one company in India. All amounts are in INR. The system accepts CGST + SGST and IGST.
  • The PO balance uses the subtotal before tax. A different check (R05) examines the tax.
  • The ledger starts with 2 invoices “imported from ERP”. The knowledge base starts with 16 past reviewer decisions. Thus, the duplicate, PO balance and precedent functions have history.
  • The upload area replaces an email inbox. The same pipeline can receive invoices from an inbox.
  • The system compares the invoice with the PO only. It does not compare with the goods receipt (no 3-way match).
  • The system does not make payments. It sends approved invoices to the payment run queue.
  • The layout model was trained and validated on synthetic pages only. We did not measure it on real invoices.
  • The system detects handwriting. It does not read handwriting. Detection is sufficient for the policy, because the policy does not accept handwritten changes.
  • The clean-up and layout stages use a maximum of 4 pages for each document.
  • The layout model uses Ultralytics YOLO (AGPL-3.0 licence). For commercial use, buy a licence or use a different detector with the same ONNX interface.

LedgerThe list of invoices that are approved for payment.
OCROptical character recognition. Software that reads text in an image.
OSDOrientation and script detection. A Tesseract function that finds if a page is sideways or upside down.
LegibilityHow clearly the system can read a page. The system measures it with OCR after clean-up, as a score from 0 to 100.
RegionOne area of the page that the layout model finds, for example the totals, the bank block or a stamp.
YOLOA type of object detector. The system uses YOLO11n to find the regions.
mAPMean average precision. A measure of detector accuracy, from 0 to 1. mAP@50-95 is stricter than mAP@50.
PrecedentA past reviewer decision on the same type of exception, with the reviewer note.
Hybrid searchA search that combines keyword search (BM25) and search by meaning (embeddings).
EmbeddingA list of numbers that shows the meaning of a text. Texts with a similar meaning have similar embeddings.
RRFReciprocal rank fusion. A method that combines two lists of search results into one list.
Dual readTwo independent reads of the same page (AI model and OCR). The system compares them.
AblationA test with one part of the system off. It shows the value of that part.
FingerprintA SHA-256 value of the file. Two identical files have the same value.
SSEServer-Sent Events. The method that sends live updates to the browser.
Fail safeWhen an error occurs, the system goes to the safe state (on hold), not to approval.
